## Context

项目当前是 Python 桌面应用，主要入口为 `run_gui.py`，界面层集中在 `gui/`，总结、拆章、状态、提示词、API 调用等业务逻辑集中在 `logic/` 和 `splitters/`。现状中有三个明显约束：

- 现有模块大量使用 `python.gui.*`、`python.logic.*` 导入路径，但仓库当前根目录下并没有 `python/` 包目录，入口和模块注释也保留了历史路径假设。
- `gui/` 的 mixin 同时负责控件状态、参数校验、线程/事件循环、日志队列和业务调用，迁移 WebUI 时需要先抽出稳定的服务边界。
- 部分逻辑存在不一致迹象，例如 `article_summary_logic.py` 调用的状态函数和 LLM 封装参数与当前 `state_manager.py`、`llm_api.py` 实现不匹配，适合纳入重构前的修复清单。

## Goals / Non-Goals

**Goals:**

- 用本地 WebUI 替代 CustomTkinter 作为主交互入口，提供更现代、清晰、可扩展的界面。
- 保留现有核心能力：小说总结、文章总结、自定义总结、章节分割、提示词编辑、API 配置、日志展示、暂停/取消和断点续跑。
- 将 UI、任务运行时、配置管理和纯业务逻辑拆开，减少 GUI 控件状态直接驱动业务代码。
- 形成一组可确认的逻辑优化点，实施前由用户决定优先级和范围。

**Non-Goals:**

- 不在本变更中改造为公网多用户服务。
- 不更换 LLM API 协议或重写提示词体系。
- 不改变现有 `.summarizer_cache` 输出目录语义，除非后续明确批准迁移。
- 不引入数据库作为必需依赖；默认继续使用本地 JSON/文件缓存。

## Decisions

### Decision 1: 采用本地 Web 服务 + 浏览器前端

确认方案：后端使用 FastAPI，前端使用 React + Vite + TypeScript，并通过 REST + SSE 或 WebSocket 连接任务状态和日志。

理由：

- FastAPI 与现有异步总结流程、`httpx`、`asyncio` 更匹配。
- React/Vite 更容易做出现代化工作台、分栏日志、任务卡片、配置表单和响应式布局。
- REST 用于配置和任务操作，SSE/WebSocket 用于日志和进度流，边界清晰。

备选方案：

- Streamlit/Gradio/NiceGUI：实现更快、Python-only，但复杂任务控制、配置编辑和长日志工作台会更受框架限制。
- Flask + 简单模板：依赖少，但异步任务、实时日志和大型表单体验需要更多手写代码。

### Decision 2: 先抽象任务运行时，再接入 WebUI

新增任务运行时服务，统一管理四类任务：小说总结、文章总结、自定义总结、章节分割。每个任务都有 `task_id`、状态、进度、日志流和控制操作。

理由：

- 当前 GUI 中的 `backend_thread`、`backend_loop`、`backend_task`、`splitter_thread`、`log_queue` 和 `gui_queue` 分散在 mixin 与主类中，直接迁移会把旧耦合搬到 Web 层。
- 统一任务模型能让 WebUI、未来 CLI 或兼容启动器复用同一套业务入口。

备选方案：

- 直接把现有 GUI 回调替换为 HTTP 回调：改动短期更小，但会保留线程/队列耦合，后续维护成本高。

### Decision 3: 配置管理从控件状态迁移到显式数据模型

新增配置服务，使用结构化模型读写 API 配置、提示词、字数设置和任务参数。WebUI 表单只负责展示和提交数据，不直接成为业务状态源。

理由：

- 当前 `api_manager.py` 和 `event_handlers.py` 中大量通过控件变量同步配置，难以测试。
- 显式模型可以做统一校验、默认值填充、敏感字段遮蔽和迁移兼容。

备选方案：

- 保持现有 JSON 结构并在前端直接拼装：短期简单，但校验分散，错误提示和兼容迁移更脆弱。

### Decision 4: API Key 使用本地配置文件 + 环境变量覆盖

确认方案：继续支持在本地配置文件中保存 API Key，同时允许配置项指定环境变量名；运行时优先读取环境变量，环境变量不存在时再回退到本地配置文件中的 Key。

理由：

- 保留本地配置文件保存能力，普通用户仍可在 WebUI 中完成配置。
- 支持环境变量覆盖后，用户可以避免把真实 Key 写入项目文件，更适合分享配置、提交代码或后续自动化运行。
- 后端统一解析真实 Key，前端默认只看到遮蔽值或环境变量引用，降低泄漏风险。

备选方案：

- 仅本地配置文件保存：最简单，但泄漏风险更高。
- 仅环境变量保存：更安全，但对普通本地用户不够友好。

### Decision 5: 逻辑优化纳入本次迁移，但拆成小步实施

本次迁移同时处理已发现的逻辑问题和结构优化，但必须按依赖拆成小任务逐步验证，避免一次性重写全部业务逻辑。

确认纳入本次的优化点：

1. 修复导入路径与包结构：统一为仓库实际包路径，避免 `python.*` 历史路径导致启动失败。
2. 修复文章总结流程：对齐 `get_llm_summary_with_config` 调用签名，补齐或替换不存在的异步状态读写函数。
3. 抽离任务运行时：把线程、事件循环、暂停、取消、日志队列从 GUI mixin 移入后端服务。
4. 抽离配置模型：将 API 配置、提示词、字数设置、任务参数从控件变量中解耦。
5. 统一日志事件格式：让 GUI/后端/文件日志都使用同一结构，减少 `source_id`、`api_id_for_log`、`display_name` 混用。
6. 统一文件路径和缓存服务：集中处理 `.summarizer_cache`、`prompt_cache`、输出目录、编码读取和安全文件名。
7. 收敛重复排序/拆章工具：`logic.utils`、`logic.chapter_splitter` 和 `splitters/*` 中存在相近的文件名清理、章节写入和排序逻辑。
8. 为核心纯逻辑补测试：优先覆盖章节排序、状态恢复、配置校验、API 错误判断和文章总结流程。

### Decision 6: 旧 CustomTkinter GUI 作为过渡层，WebUI 稳定后移除

迁移过程中保留旧 `gui/` 和 `run_gui.py` 的兼容能力，避免 WebUI 尚未完成时破坏现有入口。WebUI 完成并通过冒烟测试后，移除 CustomTkinter GUI 相关代码和依赖。

理由：

- 保留过渡入口可以降低迁移风险。
- WebUI 稳定后移除旧 GUI 能避免长期维护双套界面、双套任务控制和双套配置同步。

备选方案：

- 长期保留旧 GUI：兼容性更强，但维护成本高，不符合本次重构目标。

## Risks / Trade-offs

- [引入前端工具链增加依赖和构建步骤] → 提供单一启动脚本，开发模式启动后端和前端，发布模式由后端托管构建产物。
- [大规模迁移导致现有功能退化] → 先用任务运行时包住现有 `logic/`，逐步替换 GUI 层，不重写提示词和总结算法。
- [实时日志通道复杂度上升] → 首选 SSE；如果需要双向控制或多客户端再升级 WebSocket。
- [API Key 在 WebUI 中泄漏风险] → 后端保存密钥，前端默认只显示遮蔽值；日志和响应不得返回完整密钥。
- [Windows 本地路径和中文路径兼容问题] → 后端继续使用 Python 文件 API，新增针对中文路径、空格路径和不同编码文本的测试。

## Migration Plan

1. 建立后端服务入口和前端应用目录，但先只提供健康检查和静态页面。
2. 抽出配置服务，迁移 API 配置、提示词和字数设置的读写接口。
3. 抽出任务运行时，把现有小说总结、文章总结、自定义总结和章节分割接入统一任务模型。
4. 实现 WebUI 工作台页面，逐步替代 `gui/` 中的表单和日志视图。
5. 保留 `run_gui.py` 为过渡入口：可提示用户运行 WebUI，或启动本地 Web 服务并打开浏览器。
6. 补充核心逻辑测试和最小端到端冒烟检查。
7. 在 WebUI 和文档中加入原作者与现作者署名。
8. WebUI 稳定后移除 CustomTkinter GUI 代码、依赖和旧入口说明。

回滚策略：在 WebUI 可用前不删除 `gui/`；每个阶段保持现有核心逻辑可直接调用。若 WebUI 迁移失败，可保留旧 GUI 入口并仅合入已验证的逻辑修复。旧 GUI 删除只在 WebUI 验证完成后执行。
