## Context

`docs/stability_audit/user-facing-priorities.md` 把第二轮稳定性审计中最容易影响用户体验和前端重构风险的事项压缩为四个前置主题：旧雷点报告兼容状态、API 尝试次数与解析重试语义、任务事件订阅缓存清理、核心页面流回归基线。

现有 specs 已经定义了 `partial_failed`、任务事件 replay cursor、WebUI 终态展示和项目状态刷新等行为。本 change 不重新设计这些机制，而是在用户可见边界上补齐缺失的状态标记、文案和测试基线。

## Goals / Non-Goals

**Goals:**

- 让旧版 `failed + findings` 雷点报告保持可读，但不会被用户误读为完整成功报告。
- 让 API 配置中的 `max_retries` 继续表示总尝试次数，并在 UI 文案中明确这一点。
- 将雷点扫描解析失败重试与 API 单次请求总尝试次数拆开命名和测试。
- 在任务终态刷新完成后清理前端 per-task replay cursor 与已处理事件集合。
- 在前端重构前，用 focused tests 固定最容易回退的核心页面状态流。

**Non-Goals:**

- 不迁移或重写历史雷点报告文件。
- 不引入新的 LLM 聚合方案、prompt 结构或重试框架。
- 不做 PromptEditor 脏状态规范化、raw regex 真实超时或内部服务拆分。
- 不一次性补齐完整端到端测试矩阵；真实浏览器长任务流可保留为后续冒烟。

## Decisions

1. 用只读兼容元数据标记旧报告。

   后端读取旧版 `failed + findings` 报告时暴露 additive 的 legacy/compat warning 或兼容状态字段，前端据此显示“历史部分失败”一类状态。相比批量迁移历史文件，这个方案改动小、可回滚，并且不会破坏用户已有报告。

2. 保持 `max_retries` 的存储语义，只调整命名和说明。

   `max_retries` 继续表示一次 API 请求最多总尝试次数，避免修改既有配置文件含义。UI 将展示为“API 总尝试次数”或等价文案；后端校验和默认值保持兼容。相比重命名配置字段，这能减少迁移成本，同时修正用户预期。

3. 为雷点扫描解析失败重试使用独立概念。

   雷点扫描 pipeline 使用独立的 `parse_retries` 或同等内部命名描述“模型返回不可解析 JSON 后再次请求/解析”的次数。解析重试如果触发新的 API 请求，每次请求仍按 API 配置的总尝试次数执行；最终错误需要说明是 API 尝试耗尽、解析重试耗尽，还是两者共同导致失败。

4. 终态刷新完成后再清理前端订阅缓存。

   `useTaskActions` 当前需要 replay cursor 和 seen event id set 来处理断线重连与重复事件。清理应发生在终态事件触发、最新任务状态刷新完成、订阅关闭之后，避免过早清理导致终态状态丢失；清理范围只限对应 task，不影响其他活跃任务。

5. 回归基线优先使用 focused frontend tests。

   先补最小组件/Hook 测试，覆盖任务终态文案、warning/error 展示、按钮禁用状态和项目刷新。相比直接上完整 E2E，这更贴合当前前端重构前置目标，执行成本更低，也更容易在后续页面拆分时保持稳定。

## Risks / Trade-offs

- 旧报告形态识别过宽会误标普通失败报告 -> 仅对包含可展示 findings/events 且缺少现代 `partial_failed` 语义的旧结构加兼容标记。
- “API 总尝试次数”和“解析重试”两个概念可能增加文案复杂度 -> UI 只在配置和失败提示中展示必要说明，避免到处重复解释。
- 终态清理过早可能影响最终状态展示 -> 把清理放在终态刷新 promise 完成之后，并用 `useTaskActions` focused test 锁住顺序。
- 回归基线不覆盖真实长任务浏览器流 -> 本 change 先覆盖可自动化的核心状态流，长任务手工/轻量冒烟留给后续重构验证。

## Migration Plan

- 既有 API 配置文件不迁移，按现有 `max_retries` 总尝试次数语义继续读取。
- 既有旧雷点报告文件不改写，只在读取和展示时添加兼容提示。
- 前端订阅缓存清理只影响新运行时内存状态，不改变持久化任务事件日志或后端 replay 行为。

## Open Questions

- `parse_retries` 是否作为用户可配置项暴露，还是先作为内部常量/扫描配置字段实现，应在实现时按现有配置表单复杂度决定。
