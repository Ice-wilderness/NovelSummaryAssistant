## Why

第二轮稳定性审计发现几处会直接影响用户理解、等待预期、结果可信度和前端重构风险的边界问题。先把这些用户可见边界收紧，可以在进入页面结构重构前固定关键状态语义与核心交互基线。

## What Changes

- 为旧版 `failed + findings` 雷点扫描报告保留可读性，同时在 API 或前端显示中明确标记为历史兼容/旧版部分失败结果。
- 澄清 API `max_retries` 的用户含义为总尝试次数，并把雷点扫描解析失败重试建模为独立的解析重试概念，避免叠加调用次数超出预期而没有提示。
- 在前端任务事件订阅中，于任务终态刷新完成后清理对应任务的 replay cursor 与已处理事件集合，降低长会话内存增长风险。
- 为前端重构前的核心用户路径补最小回归基线，覆盖任务终态文案、错误与 warning 展示、按钮禁用状态和项目状态刷新。
- 不包含 PromptEditor 脏状态比较、raw regex 超时强化、内部服务拆分、LLM 聚合方案或发布前打包态专项冒烟。

## Capabilities

### New Capabilities

- None.

### Modified Capabilities

- `trigger-scan-results`: 增加旧版雷点扫描报告兼容状态的 API/展示语义，避免把旧部分失败报告误导为完整成功。
- `trigger-scan-workflow`: 明确 API 总尝试次数与雷点解析重试的边界，并要求最终失败提示说明相关重试耗尽情况。
- `configuration-management`: 澄清 API 配置中 `max_retries` 面向用户的含义，要求界面文案与保存/加载语义一致。
- `webui-workbench`: 增强任务事件订阅终态清理要求，并为前端重构前的核心页面流建立可测试的用户体验基线。

## Impact

- 后端雷点报告读取、报告列表/详情 API 数据模型，以及旧报告兼容转换逻辑。
- 雷点扫描 pipeline 中解析失败重试的配置、命名、日志和失败提示。
- API 配置页面与相关类型/默认值展示文案。
- `useTaskActions` 任务事件订阅状态管理与 focused tests。
- 前端核心页面流测试，覆盖小说总结、文章/自定义总结、章节分割、雷点报告查看等重构前高风险路径。
