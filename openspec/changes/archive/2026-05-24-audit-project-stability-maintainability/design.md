## Context

当前项目同时包含 Python 后端与核心逻辑、React/Vite 前端、OpenSpec 变更记录、测试套件、配置文件、运行时输出目录和历史迁移文档。近期已有大量需求与代码变更，且过程里出现过多次缺陷修复，因此这次 change 的重点是建立一次可复查的模块级审计产出，而不是立即改动业务代码。

审计结果统一写入 `docs/stability_audit/`，按模块拆分报告，并提供总览与跨模块风险汇总。报告需要覆盖前端、WebUI 后端、核心总结流程、触发词扫描、章节拆分、配置与文件工作区、运行时状态与输出、测试与 OpenSpec/文档等边界。

## Goals / Non-Goals

**Goals:**
- 盘点项目主要模块的职责、关键入口、关键数据流和外部契约。
- 按模块输出稳定性风险、潜在坑、可维护性问题和优化空间。
- 对每个发现标注证据、风险级别、影响范围和建议处理方向。
- 汇总跨模块风险，形成后续可拆分为 OpenSpec change 或 issue 的改进候选项，并在总览中标注建议修复顺序和预计改动复杂度。

**Non-Goals:**
- 不在本 change 中修复发现的运行时问题。
- 不修改运行时行为、API、前端交互、配置格式或依赖版本。
- 不把审计报告写成测试结果的替代品；测试结果只作为审计证据之一。

## Decisions

1. 报告以 `docs/stability_audit/` 为唯一输出目录。这样能让审计产物与现有运行时代码隔离，后续也便于删除、归档或继续补充。备选方案是把报告散落到各模块目录，但这会增加查找成本并混入源码维护边界。

2. 模块划分按职责和运行时边界进行，而不是简单按目录树进行。核心模块包括前端工作台、WebUI API/服务层、总结与编排逻辑、触发词扫描流程、章节拆分与模式配置、配置/文件/工作区管理、运行时状态与输出、测试与规格文档。这样能覆盖跨目录协作风险，例如前端状态与后端任务状态、上传文件与工作区输出、OpenSpec 契约与实现漂移。

3. 每个风险发现使用统一字段：现象、证据、影响、风险级别、建议。备选方案是自由格式长文，但统一字段更利于后续筛选高优先级问题。

4. 审计以静态阅读为主，辅以现有测试和可运行检查。若某些检查因环境或依赖限制无法执行，报告需要明确记录未验证范围，避免把推测写成事实。

5. 最终总览必须包含建议修复顺序和预计改动复杂度。建议修复顺序用于帮助后续拆分 change 或 issue，预计改动复杂度用于区分小修、局部重构和跨模块治理。备选方案是只列风险级别，但风险级别不能反映落地成本。

6. 审计过程中允许运行完整测试套件，也允许为验证审计结论编写和运行有针对性的测试。必要的新增测试应只服务于验证风险或复现边界行为；如果需要额外授权、依赖安装或长时间运行，应在执行时请求确认并在报告中记录。

## Risks / Trade-offs

- 审计范围过大导致报告过浅 -> 使用模块清单和关键文件清单确认覆盖面，并在总览中记录未深入区域。
- 静态分析可能误判运行时行为 -> 对发现区分“已由代码证据确认”和“需要运行验证”，必要时引用测试或手工检查结果。
- 报告产生大量低价值建议 -> 按风险级别和维护收益排序，优先记录会影响稳定性、数据正确性、用户流程或未来开发效率的问题。
- 实现阶段顺手修代码导致范围失控 -> 本 change 只产出文档；修复项应作为后续独立 change 处理。
- 完整测试或新增验证测试可能耗时较长 -> 优先运行现有套件和高风险模块的目标测试，并在总览中记录执行命令、结果和未覆盖范围。

## Migration Plan

无需运行时迁移。实现阶段主要新增 `docs/stability_audit/` 下的 Markdown 报告；如为审计准确性新增测试，测试文件必须保持在测试边界内且不改变运行时行为。回滚时删除该目录、相关测试补充和本 change 产物，不影响应用行为。
