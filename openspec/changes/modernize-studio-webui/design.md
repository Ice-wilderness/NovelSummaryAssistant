## Context

现有 WebUI 基于 React/Vite/TypeScript，功能覆盖较完整：小说总结、文章总结、自定义总结、章节分割、雷点扫描、提示词编辑、API 配置、项目历史、输出目录、修复建议、实时任务控制和日志。当前界面主要由左侧导航、中间页面和右侧日志组成，样式集中在 `frontend/src/styles.css`，组件散布在 `components/layout`、`components/forms`、`components/logs`、`views/*` 和 `views/trigger-scan/*`。

用户已选择“B 写作工作室”方向，但明确要求 demo 只是方向参考，正式页面必须围绕项目真实功能重新设计。目标使用场景是 PC 桌面宽屏，不要求移动端完整适配。用户也明确允许新增前端库、扩展或插件，以提升现代化、美观度、动效和交互舒适度。

## Goals / Non-Goals

**Goals:**

- 将 WebUI 设计成 PC 优先的写作工作室，而不是对现有三栏结构做简单换皮。
- 让项目、章节、任务阶段、当前步骤、配置、产物、雷点扫描和日志之间的关系更清晰。
- 通过现代视觉系统和动效提升高级感，同时保持长任务工具所需的信息密度和可读性。
- 保留现有后端 API 和业务能力，优先做前端信息架构、组件结构、视觉和交互重构。
- 允许引入适合的外部前端库，但每个依赖都必须服务可访问性、动效、布局、状态反馈或开发效率。
- 建立可验证的改造路径，避免一次性重写导致功能回归。

**Non-Goals:**

- 不以移动端体验为目标；只保留基础窄宽容错。
- 不改变总结、分割、雷点扫描、修复任务的后端业务语义。
- 不把静态 demo 逐像素照搬到生产页面。
- 不为了美化隐藏关键配置、日志、错误、警告或修复风险。
- 不在第一阶段引入需要远程服务、用户登录、云同步或后端架构变化的 UI 平台。

## Decisions

### Decision 1: 使用“工作室壳 + 当前步骤面板 + 底部日志时间线”的 PC 信息架构

正式实现应将主界面拆成稳定的 PC 工作台区域：

- 顶部：项目/工作流标题、当前任务状态、全局任务控制。
- 左侧：工作流导航、项目历史、章节/报告/提示词等上下文索引。
- 中央：当前工作流的主画布，优先呈现上传、分割预览、阶段流、产物预览或报告审阅。
- 右侧：当前步骤操作面板，承载本页最相关的操作、修复建议、配置快捷项或扫描复核。
- 底部或可展开区域：实时日志时间线，允许切换全局/API 来源并查看详情。

Rationale: 这能保留真实功能密度，又让用户始终知道“我在哪个项目、哪个阶段、下一步做什么”。

Alternative considered: 继续保留现有左中右三栏，只升级视觉。Rejected because 用户已指出这与“完全重构”差距较大。

### Decision 2: 将视觉系统集中成可复用设计层

实现应优先抽出新的布局与展示组件，而不是继续在单个全局 CSS 文件中无限追加页面级样式。建议分层：

- `StudioShell` / `StudioLayout`: 工作台壳、区域布局、顶部任务状态、底部日志入口。
- `StudioNavigation`: 工作流导航和上下文索引。
- `StudioPanel` / `StudioCard` / `StudioSection`: 页面内常用容器。
- `StudioStageFlow`: 阶段流，可复用现有 `StageProgressBar` 数据。
- `StudioInspector`: 当前步骤操作面板。
- `StudioLogTimeline`: 重新呈现现有日志数据。

Rationale: 重构会跨多个页面，集中设计层能减少重复和后续维护成本。

Alternative considered: 单纯重写 `styles.css`。Rejected because 难以控制长期复杂度，也不利于分阶段迁移。

### Decision 3: 外部库允许引入，但先服务体验基础设施

可以优先评估并引入以下类别依赖：

- 动效：例如 `framer-motion` 或同类 React 动效库，用于页面入场、面板切换、阶段流、日志追加和状态变化。
- 无障碍交互原语：例如 Radix UI 的 Tabs、Dialog、Tooltip、Popover、ScrollArea 等，以提升复杂控件的键盘和焦点行为。
- 样式组织：可考虑 CSS Modules、vanilla CSS 分层、或轻量 class 合成工具；若引入 Tailwind/UnoCSS 等原子化方案，应先确认不会造成大规模迁移噪音。
- 数据/状态辅助：仅在现有 state/hook 结构难以支撑新交互时再引入。

Rationale: 用户明确允许外部库；高质量动效和复杂交互不应全部手写。但依赖必须提高体验或可靠性。

Alternative considered: 不新增任何依赖。Rejected because 会限制动效和高级交互质量，且增加手写复杂度。

### Decision 4: 分阶段迁移，不一次性改完所有页面

建议实施顺序：

1. 建立 Studio layout/design foundation，并保持现有页面仍可运行。
2. 迁移共享任务状态、日志、阶段流、项目上下文。
3. 优先迁移小说总结页，因为它包含上传、项目、阶段、修复、输出目录和参数，是最能验证新信息架构的页面。
4. 迁移雷点扫描页，重点验证报告审阅、上下文、过滤和复核。
5. 迁移文章/自定义总结、章节分割、提示词、API 配置。
6. 清理旧布局样式和过渡兼容层。

Rationale: 小说总结和雷点扫描覆盖最多真实复杂度，先迁移它们能尽早暴露设计问题。

Alternative considered: 一次性重写所有 views。Rejected because 回归风险高，测试定位困难。

### Decision 5: 动效必须表达状态变化，不遮蔽任务信息

动效应覆盖：

- 页面或工作流切换的入场/退场。
- 当前阶段推进、任务运行、暂停、取消、终止状态变化。
- 日志追加和警告出现。
- 操作面板 tab 切换、修复建议展开、报告上下文打开。
- hover/focus 的轻量反馈。

动效不得：

- 延迟关键错误、警告、确认或风险说明。
- 导致长日志、长文件名、长路径不可读。
- 让任务状态看起来已完成但实际仍在运行。

Rationale: 高级感来自“状态有回应”，不是动画堆叠。

## Risks / Trade-offs

- [Risk] 新布局过度概念化，导致真实功能入口变深。 → Mitigation: 每个页面迁移时列出原功能清单并做功能对照检查。
- [Risk] 新依赖增加包体和维护成本。 → Mitigation: 每个依赖在任务中说明用途，并通过 build/typecheck/test 验证；避免同类库重复。
- [Risk] 动效影响低性能设备或长列表操作。 → Mitigation: 对长日志和列表使用轻量动效，提供可降级 CSS/React 实现，避免对大量节点做持续动画。
- [Risk] 大规模 CSS 重构引发视觉回归。 → Mitigation: 建立新 design layer 后逐页迁移，旧样式只在对应页面迁移完成后清理。
- [Risk] 页面结构变化导致现有测试大量失效。 → Mitigation: 先更新语义化角色、可访问标签和测试查询策略，再迁移视觉结构。
- [Risk] PC 优先导致窄屏不完善。 → Mitigation: 明确非目标，只保证不出现关键内容完全不可达；主要验收使用 PC 宽屏。
