## Context

当前 WebUI 已经改为上传文件驱动的本地单用户工作台，但仍保留少量本地路径能力：自定义输出目录、文件/目录选择器和打开输出目录。稳定性审计指出，主动保存或启动任务时的无效自定义输出目录仍可能回退默认目录，配置 JSON 损坏时会恢复默认值但缺少备份和用户提示，headless、无 tkinter 或打包环境中的本地能力失败也缺少清晰反馈。

本 change 的目标是收紧“主动操作”的失败语义，同时保留旧项目兼容：用户新保存或启动任务时必须看见错误并显式选择回退默认输出目录；读取历史 metadata 时可以兼容回退，但必须携带 warning。

## Goals / Non-Goals

**Goals:**

- 明确项目的本地路径能力面向本地单用户应用，而不是远程多人部署。
- 主动保存项目或启动任务时，对无效项目级自定义输出目录返回验证错误，不静默回退。
- 在无效输出目录错误旁提供“使用默认输出目录”的显式恢复路径。
- 读取旧 metadata、历史项目或导入项目时，对无效旧自定义输出目录兼容回退默认目录，并返回 warning。
- 配置文件损坏时先备份为 `.bak`，再使用默认值，并让对应页面局部展示 warning。
- 将打开目录能力限制为当前项目有效输出目录，并在本地能力不可用时返回可操作错误。
- 补充后端和前端 focused tests。

**Non-Goals:**

- 不移除本地文件/目录选择器。
- 不支持远程服务器安全模型或多用户隔离。
- 不新增通用任意路径打开 API。
- 不实现配置恢复历史管理、配置 diff 或自动合并损坏配置。
- 不改变上传文件大小上限或改为流式上传。

## Decisions

### 1. 主动验证和兼容读取使用不同路径

`resolve_output_selection` 或其下层 helper 应区分两类调用：

- `strict`：用于保存项目、迁移输出目录、启动任务前 auto-save。自定义输出目录不存在、不是目录或不可访问时直接抛出验证错误，并保留既有保存值。
- `compat`：用于加载旧 metadata、历史项目、项目详情和导入项目。旧自定义目录不可用时回退有效默认目录，并把原路径和原因写入 warning。

理由：主动操作代表用户刚做出的选择，静默回退会让输出写到意料之外的位置；历史读取则应尽量可打开项目，不因旧路径损坏而阻塞页面。

替代方案：所有场景都严格报错。缺点是旧项目或移动过目录的历史记录会更难恢复。

### 2. 默认目录回退必须是显式用户动作

前端收到无效自定义输出目录错误后，保留用户输入的无效路径供修改，并在输出目录控件附近显示“使用默认输出目录”动作。用户点击后，下一次 save/task-start 请求应清空 `custom_output_directory_path`，让后端按用户默认导出目录或 fallback exports 解析输出目录。

理由：用户仍可修正路径，也可以明确接受默认目录；系统不替用户静默改写输出目标。

替代方案：后端在错误响应中直接返回默认目录并自动保存。缺点是行为接近原有静默回退，用户仍可能误判输出位置。

### 3. 配置损坏恢复集中到配置加载边界

`load_api_configs`、`load_user_settings` 和 chapter pattern 加载路径应复用一个小型备份/告警策略：

- 捕获 JSON 解析失败或结构无法使用的损坏文件。
- 尝试复制原文件到同目录 `.bak` 文件；若 `.bak` 已存在，可使用带时间或序号的 `.bak` 变体，避免覆盖已有备份。
- 返回默认值和机器可读 warning，例如 domain、message、backup_path、backup_failed。

理由：配置加载函数最接近损坏来源，能避免 API routes 各自猜测错误类型。备份失败不应阻塞默认值恢复，但必须进入 warning。

替代方案：只在 API route 层捕获并备份。缺点是命令行或测试直接调用配置服务时不会获得一致行为。

### 4. 打开目录由项目输出目标派生

打开输出目录的后端路径应优先通过 project slug 和当前项目 metadata 解析有效输出目录，而不是信任前端传入任意本地路径。若保留兼容字段，后端也必须验证其等于当前项目有效输出目录；否则拒绝。

理由：这个动作是“打开项目输出目录”，不是通用本地文件管理器。限制边界可以减少误打开敏感路径和不同调用方语义漂移。

替代方案：继续允许显式 path。缺点是安全边界难以解释，也和本轮“仅输出目录”的确认不一致。

### 5. warning 在对应页面局部展示

后端 response 增加可选 warning 字段，前端把 warning 显示在最接近的页面或控件：

- API 配置损坏：API 设置页或 API 配置区域。
- 用户设置损坏：用户设置页或设置区域。
- 章节模式损坏：章节模式/章节分割相关页面。
- 自定义输出目录错误：输出目录控件附近。
- 本地 picker/open 失败：触发按钮附近。

理由：这些问题都有明确修复位置，局部展示比全局 banner 更利于用户行动，也避免 unrelated 页面被配置恢复噪音打断。

## Risks / Trade-offs

- 旧测试可能依赖无效自定义目录回退 -> 更新测试期望，保留历史读取的兼容回退场景。
- `.bak` 写入也可能失败 -> 不阻塞默认值恢复，但 warning 必须说明备份失败。
- response 增加 warning 字段会触及类型定义 -> 使用可选字段，保持旧 response 兼容。
- 前端同一输出目录控件被多个页面复用程度有限 -> 优先改共享控件或 helper；若页面差异较大，先补 focused tests 覆盖主要工作流。
- 打开目录 API 收紧可能影响显式 path 调用 -> 保留项目输出目录打开用例；非输出目录调用返回清晰 validation error。
- headless/frozen 环境难以完整自动化 -> 通过 monkeypatch local picker/open helper 的失败分支做后端测试，前端测试验证错误展示。

## Migration Plan

1. 后端先增加配置恢复 warning model 和 `.bak` 备份 helper，保持现有默认值返回。
2. 将输出目录解析拆成 strict/compat 调用点，先覆盖保存项目和任务启动前 auto-save，再覆盖历史/详情读取 warning。
3. 收紧打开输出目录 route，使其从项目输出目标派生并拒绝非输出目录 path。
4. 前端补 API 类型和局部 warning 展示，再增加默认目录回退按钮行为。
5. 补 focused tests 后运行相关 Python tests、前端 Vitest、`npm run build` 和 `openspec validate --all`。

## Open Questions

无。用户已确认本项目按本地单用户应用处理，无效自定义输出目录主动报错并提供默认目录按钮，打开目录仅限输出目录，配置 warning 在对应页面局部展示。
