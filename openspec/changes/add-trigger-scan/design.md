## Context

NovelSummaryAssistant 当前通过 WebUI 管理小说总结、文章总结、自定义总结、章节拆分、提示词和 API 配置。后端的长任务统一经由 `webui_backend.task_runtime.TaskRuntime` 运行，具体工作流 runner 位于 `webui_backend.workflow_services`，小说总结由 `logic.orchestrator` 和 `logic.summarization_stages` 编排，章节拆分由 `logic.chapter_splitter` 分发到 `splitters/*_strategy.py`。

雷点扫描依赖三个现有基础：托管项目输出目录、结构化提示词、SSE 日志/进度流。但它也暴露出现有架构的关键限制：章节拆分粒度与小总结粒度耦合，`chapters_per_file` 会产生多章合并文件，无法给扫描结果提供稳定段落定位。因此本变更需要同时新增扫描能力，并重构章节文件与总结批量粒度。

## Goals / Non-Goals

**Goals:**

- 将章节拆分固定为一章一个文件，使后续总结和扫描共享稳定章节边界。
- 用 `summary_batch_size` 替代拆分阶段的 `chapters_per_file`，在总结阶段控制小总结输入合并粒度。
- 为 `novel_summary` 项目新增雷点扫描附加工作流，支持混合模式、精确模式、二次验证、AI 聚合和章节级续扫。
- 提供全局雷点档案、规则分组、内置规则模板和扫描默认配置。
- 将扫描结果、历史记录、跳读清单、导出报告纳入项目输出目录。
- 复用现有 API 配置、提示词编辑、任务运行、项目历史和日志面板能力。

**Non-Goals:**

- 不实现 V2 范围的 token 成本预估、规则测试工具、新旧报告对比、智能规则推荐、智能规则优化、CSV/HTML 导出或章节时间线视图。
- 不引入新的外部数据库；MVP 继续使用本地 JSON/Markdown 文件。
- 不改变同一时间只能运行一个长任务的产品约束。
- 不保证 AI 结果绝对完整或正确；UI 和导出报告必须保留辅助参考提示。

## Decisions

### 1. 章节边界成为底层不变量

拆分策略仍保留 default/regex/title_list 三种入口，但 `split_novel_into_chapter_files` 不再接受用户配置的 `chapters_per_file`，内部固定按 1 章写一个文件。输出文件名使用 `第001章.txt`、`第002章.txt` 等稳定格式；章节标题作为文件内容或元数据的一部分保留。

原因：雷点扫描、段落缓存、上下文查看和续扫都需要“一个文件等于一个章节”的稳定前提。继续允许多章合并会让段落 ID、章节范围、跳读清单和扫描报告都变得含糊。

备选方案：在扫描时临时拆分多章文件。该方案会让同一项目中总结输入和扫描输入不一致，且更难解释续扫/迁移状态，因此不采用。

### 2. 总结批量粒度下沉到小总结阶段

`NovelSummaryRequest` 新增 `summary_batch_size`，新项目默认值为 10，后端传入 `run_small_summary_stage`。小总结阶段按单章文件列表组批，把每批多个章节合并为一次 LLM 输入，输出仍写入小总结缓存。`big_summary_batch_size` 继续只控制大总结阶段。

原因：用户想控制的是总结成本和 token 粒度，不应改变章节文件结构。这样雷点扫描可以逐章精扫，而总结仍可保持经济批量。

备选方案：保留拆分批量并额外生成单章索引。该方案会增加双份章节来源和同步成本，旧问题仍会在用户查看原文时出现，因此不采用。

### 3. 旧项目通过显式检测和可确认迁移进入新架构

项目导入、打开、启动总结或启动扫描前，后端检测章节目录中是否存在 `第N章-第M章.txt` 或单文件多章节特征。检测到旧格式时，WebUI 提示用户需要重新拆分；确认后后端优先直接解析多章合并文件并重拆为单章文件，并把旧 `chapters_per_file` 或检测到的合并跨度保存为该项目的 `summary_batch_size`。如果合并文件解析失败，WebUI 允许用户手动选择原始整本 TXT 重新拆分作为兜底路径。

原因：这是破坏性数据布局变更，必须避免静默改变用户现有输出。迁移后保留原总结粒度意图，降低用户重新配置成本。

备选方案：自动静默迁移。该方案更顺滑但风险高，用户难以理解为什么文件数量和后续总结批次变化，因此不采用。

### 4. 雷点扫描作为托管长任务接入 TaskRuntime

新增 `TaskType.TRIGGER_SCAN` 和 `create_trigger_scan_runner`。扫描 runner 调用新的 `logic.trigger_scan` 模块族，阶段包括：

- `paragraph_index`: 章节标题识别、段落编号、长章节 chunk 与缓存。
- `coarse_scan`: 混合模式读取小总结粗筛疑似章节。
- `precise_scan`: 对疑似章节或全部章节原文进行严格 JSON 精扫。
- `verification`: 可选二次验证，同章 findings 批量验证。
- `aggregation`: 相邻段落自动合并，跨章节事件由 AI 辅助聚合。
- `reporting`: 保存 ScanReport、历史索引、导出文件和跳读清单更新。

原因：扫描是可暂停、可取消、可续扫、会产生实时日志的长任务，复用现有 TaskRuntime 和 SSE 能减少新基础设施。

备选方案：扫描作为普通同步 API。该方案对长篇小说和多 API 扫描不现实，且无法展示阶段进度和中间结果，因此不采用。

### 5. 扫描状态独立于总结 StateManager，但复用其思想

新增扫描状态文件 `.summarizer_cache/scan_state_{task_id}.json`，记录扫描配置快照、规则版本、章节状态、阶段状态、已产出的 finding/event/report 临时数据和最后完成章节。段落索引独立缓存到 `.summarizer_cache/paragraph_index/`，key 包含章节文件路径、mtime/size 或内容 hash。

原因：总结的 `StateManager` 面向小结/大结/超级总结阶段，直接塞入扫描状态会扩大既有类职责。独立状态文件更容易支持规则变更提醒和历史扫描隔离。

备选方案：扩展 `StateManager` 存所有扫描字段。该方案复用更多代码，但会使总结与扫描状态相互污染，不利于后续维护。

### 6. 结果模型以 report 为最终边界

每次扫描生成一个 ScanReport，包含配置快照、summary、events 和 findings。历史扫描下拉读取 `exports/{slug}/trigger_scan/reports/index.json` 或目录扫描结果。跳读清单独立保存，条目引用 `source_finding_id`，但不随报告删除而自动丢失，除非用户删除对应清单项。

原因：同一本书可使用不同档案重复扫描，结果必须可独立保存、查看、删除和导出。跳读清单是用户二次整理结果，不能被视作扫描报告的派生临时视图。

备选方案：只保留一个当前报告。该方案实现更简单，但无法支持不同档案和追更续扫场景。

### 7. 提示词节点进入现有结构化提示词系统

在 `logic.prompts.DEFAULT_PROMPTS` 和 `webui_backend.prompt_workflows` 中新增 `trigger_scan` 工作流及四个节点：`trigger_coarse_scan`、`trigger_precise_scan`、`trigger_verification`、`trigger_aggregation`。扫描模块通过 `load_all_prompts_for_run()` 获取用户编辑后的结构化消息，并在调用 `get_llm_summary_with_config` 或底层 API 包装时传入阶段变量。

原因：项目已经支持工作流提示词节点、模块、变量校验和保存/重置，雷点扫描应沿用该体系，避免出现第二套提示词编辑入口。

备选方案：把扫描 prompt 写死在扫描模块。该方案首版更快，但违背需求中的可编辑提示词，并且不利于用户调试雷点规则。

### 8. 扫描前置检查放在任务启动前

`POST /api/tasks/trigger-scan` 接收项目、档案、范围、模式和高级配置后，先执行启动前检查：

- 项目是否为旧多章合并格式。
- 混合模式所需小总结覆盖情况。
- 用户选择范围与小总结覆盖是否一致。
- 是否存在同配置可续扫状态。
- 规则版本是否较上次扫描变化。

需要用户决策的检查返回 validation payload，由前端展示明确操作：补充小总结、缩小范围、局部精确模式、迁移旧项目、取消或全部重扫。

原因：这些分支如果进入后台任务后再报错，会浪费 API 调用并让用户难以修正配置。

备选方案：后台任务遇到问题时自行降级。该方案自动化程度高，但会让扫描范围和模式不透明，因此不采用。

### 9. 仅小总结模式作为总结编排选项

`run_summarization_process` 或其上层 request 增加 `stop_after_small_summary`。该模式只执行小总结阶段，完成后返回 success，不进入大总结、超级总结或终极总结。混合扫描前置检查需要补小总结时调用该模式。

原因：当前流水线会自动推进到大总结，不适合“为了扫描而补齐小总结”的轻量操作。

备选方案：复制一套小总结 runner。该方案容易与正式总结逻辑分叉，因此优先在现有编排中增加受控停止点。

### 10. 每个功能块独立提交

实现阶段按 `tasks.md` 中的编号功能块推进。每个功能块完成并通过对应的窄范围检查后，应创建一次 git commit，再进入下一个功能块；如果某个功能块必须拆成多个可验证子块，也可以提交多个更小 commit。

原因：本变更同时触及章节拆分、总结编排、扫描核心、WebUI、导出和配置等区域，独立提交能降低回滚和代码审查成本。

## Risks / Trade-offs

- **旧项目迁移误判** → 使用文件名模式和内容章节标题双重检测；迁移前展示受影响文件数和推断批量；迁移失败不更新项目元数据。
- **AI JSON 输出不稳定** → 每个阶段使用严格 schema 解析、失败诊断和重试；解析失败的章节不标记完成。
- **漏报/误报不可避免** → UI 和导出报告固定展示辅助参考提示；提供复核、误报、正反例调整和重扫闭环。
- **跨章节聚合误合并** → 保留逐条视图，事件视图可展开查看 findings；聚合不删除原始 finding。
- **扫描成本过高** → 默认混合模式、粗筛批量默认 3、混合模式默认开启二次验证但只验证疑似章节；精确模式明确展示成本/速度提示。
- **敏感内容描述过细** → prompt 限制详细描述尺度，`evidence_quote` 默认不超过 80 字，并只在详细档展示。
- **规则变更后的续扫语义复杂** → 扫描状态保存规则版本/更新时间；续扫时提示“规则已变更”，由用户选择继续、全部重扫或新建扫描。

## Migration Plan

1. 增加新数据模型和服务，但不改变现有默认 UI 行为。
2. 更新章节拆分后端与前端：隐藏 `chapters_per_file`，固定单章输出；同时新增旧项目检测 API。
3. 更新小说总结请求与小总结阶段，加入 `summary_batch_size` 和 `stop_after_small_summary`；保持旧请求缺字段时默认使用 10 或迁移值。
4. 加入雷点档案服务和默认模板；启动时若 `workspace/trigger_profiles/` 不存在则创建默认档案/模板。
5. 接入扫描任务 API、扫描服务、提示词节点和结果存储。
6. 加入 WebUI 雷点扫描页面与导航入口。
7. 补齐导出、跳读清单、历史记录、上下文查看和结果交互。
8. 通过后端单元测试、前端类型检查和一次本地 WebUI 手动流程验证后再进入实现完成状态。

回滚策略：若扫描功能需要回滚，保留已生成的 `trigger_scan/` 和 `trigger_profiles/` 文件但隐藏导航入口；章节拆分重构属于 breaking change，回滚时需要恢复 `chapters_per_file` UI/API 并继续兼容单章文件。

## Resolved Decisions

- `summary_batch_size` 新项目默认值为 10；旧项目迁移时使用检测到的旧合并粒度。
- 旧多章合并文件重拆时优先直接解析合并文件内容；如果解析失败，允许用户手动选择原始整本 TXT 重新拆分。
