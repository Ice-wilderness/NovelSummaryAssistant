## Context

当前 WebUI 已经通过 `useManagedProject` 加载历史项目，并通过 `useTaskActions` 监听任务事件流。任务完成后，前端会更新任务记录，但不会通知项目历史列表重新读取，因此项目卡片/下拉中的 `latest_task_status` 需要刷新页面后才会变化。

历史项目 UI 目前把“新项目”作为 `<select>` 的空选项，并把状态拼接在项目名之后。长项目名会挤压状态信息；同时选择过一个项目后，再点“新项目”没有明确的重置动作，容易让用户误以为已经切回新项目。后端已有项目列表、加载、改名、清空上传文件和打开目录 API，但没有删除整个项目的 API。

当前默认导出目录固定落在运行时目录下。用户希望配置一个跨项目生效的默认导出目录，同时保留单个总结项目的自定义目录优先级，因此输出目录解析需要明确三层顺序：项目级自定义目录、用户级自定义目录、当前兜底默认导出目录。

现有 API 失败日志会把多次失败追加到同一个 JSONL 风格文件中，用户很难打开并定位某一次失败。后续诊断应改为“每次失败一个格式化 JSON 文件”，并放在独立目录中，避免与普通缓存混在一起。

当前导入已有项目后，项目输出目录不会自动指向导入目录，且项目状态通常要等到点击“开始总结”后才由总结流程顺带更新。用户期望导入项目本身就是一次恢复动作：立即设置输出目录、识别已有产物和任务状态，并在界面上展示。

项目编辑目前存在“输入即写后端”的倾向。用户删除章节文件、改名或改目录后，如果尚未保存，后端不应马上同步这些变更；“保存名称”也不足以表达保存范围。新的语义应是“保存项目”，保存项目名、章节文件、目录和相关项目元数据；若用户未保存直接开始总结，则开始前自动执行同一套保存流程。

生成质量方面，需要增加最少输出字符数限制。API 返回内容低于该限制时，应视为本次总结无效，丢弃该输出并进入既有重试流程，避免短错误提示或空洞回答被写入总结文件。

## Goals / Non-Goals

**Goals:**
- 任务进入终态后，相关工作流的历史项目列表和当前项目状态自动刷新。
- 历史项目展示改成状态标签前置、项目名独立显示，避免状态被长项目名影响。
- “新项目”成为独立按钮，负责清空当前恢复项目上下文并进入新项目流程。
- 增加删除历史项目入口，删除误建项目时不再需要手动打开资源管理器清理。
- 后端删除仅覆盖受管理的项目工作区和默认导出目录，并从历史列表移除项目。
- 增加用户级默认导出目录配置，并让项目默认输出目录按项目级、自定义用户级、兜底默认值的顺序解析。
- API 失败诊断按失败尝试拆分为单独、格式化、可读 JSON 文件，并集中放入专门的失败日志目录。
- 导入项目时立即把导入目录设为项目级输出目录，并扫描已有产物识别项目状态。
- 将“保存名称”调整为“保存项目”，并让项目名、章节文件、输出目录等修改在保存前只保留为前端草稿。
- 未保存直接开始总结时自动保存项目，保证任务使用的是最新草稿内容。
- 修改已有输出文件的导出目录时，提示用户选择是否迁移旧输出文件。
- 修正项目名称输入框为单行输入观感。
- 增加最少输出字符数配置，并在 API 返回过短时丢弃结果并重试。
- 实现阶段按同类功能块提交 git commit，便于审查和回滚。

**Non-Goals:**
- 不改变任务运行模型、上传文件格式、项目命名规则或恢复算法。
- 不引入实时推送项目列表的新通道；继续复用已有任务事件流和项目列表 API。
- 不删除用户手动指定的自定义输出目录，避免误删 WebUI 管理范围外的内容。
- 不为不同工作流分别增加独立的用户级默认导出目录；本次只提供一个跨工作流的用户级导出根目录。
- 不把未保存的前端草稿写入后端历史，也不在草稿阶段删除后端已保存的章节文件。
- 不迁移用户明确选择保留在旧目录中的输出文件。
- 不把 API key、鉴权头等敏感信息写入失败诊断日志。

## Decisions

1. 在任务终态事件处触发项目刷新，而不是轮询项目列表。

   `useTaskActions` 已能识别 `success`、`failed`、`cancelled` 并在终态事件后拉取最新任务。让启动任务的页面在 `startTask` 返回后或终态回调后调用 `project.refreshProjects()`，可以保持反馈及时，同时避免长期轮询。备选方案是定时轮询 `/api/projects`，但会增加空闲请求，也不能解释“为什么此刻刷新”。

2. 给 `useManagedProject` 增加显式 `startNewProject` 和 `deleteProject` 行为。

   `startNewProject` 负责清空 `projectSlug`、项目名、上传文件、输出目录、进度、消息和错误，使按钮语义和状态变化一致。`deleteProject` 调用后端删除 API，随后刷新列表；如果删除的是当前选中项目，则自动回到新项目状态。备选方案是在 `<select>` 的空值上复用恢复逻辑，但这会继续保留“选项即动作”的模糊交互。

3. 将历史项目控件从单一 `<select>` 调整为列表/菜单式控件，并让状态标签成为项目项的首要视觉元素。

   原生 `<option>` 无法可靠承载状态标签、删除按钮和更丰富布局。改成现有表单区中的自定义项目列表/菜单后，可以把状态标签、项目名、更新时间、恢复动作和删除动作分开呈现。若保留 `<select>`，删除按钮和标签样式都难以实现一致体验。

4. 后端删除使用显式 `DELETE /api/projects/{project_slug}`。

   服务层新增 `delete_project(project_slug)`，校验 slug 对应的元数据存在后，删除 `workspace/projects/<slug>` 和 `exports/<slug>`。不删除 `custom_output_directory` 指向的位置，因为它可能是用户选择的任意本地目录。删除不存在的项目返回可操作错误。

5. 用户级默认导出目录作为本地配置持久化，并只影响默认输出根目录。

   增加一个轻量的用户偏好配置，保存 `default_export_directory`。`ProjectWorkspaceService.default_export_dir()` 或等价解析函数读取该偏好后，将项目默认导出目录解析为 `<user_default_export_directory>/<project_slug>/<workflow_subdir>/`；未配置或配置无效时继续使用现有 `<runtime_base>/exports/<project_slug>/<workflow_subdir>/`。项目级 `custom_output_directory` 仍直接覆盖最终任务输出目录。备选方案是把用户级目录写入每个项目元数据，但这会让用户修改默认值后难以影响后续新项目，也会混淆项目级自定义与用户级偏好。

6. API 失败日志使用专门目录中的单次失败 JSON 文件。

   在每次 API 调用失败、响应解析失败、最少输出字符数校验失败或达到可诊断的重试失败点时，写入一个格式化 JSON 文件，例如 `.summarizer_cache/api_failures/<timestamp>_<api_name>_<stage>_<attempt>.json`。文件包含阶段、章节/批次、API 名称、尝试次数、错误类型、HTTP 状态、异常摘要、响应内容或截断后的响应内容，以及必要的请求上下文；敏感字段必须脱敏或省略。备选方案是继续 JSONL 追加，但它不利于普通用户直接查看，也难以单独分享某次失败。

7. 项目编辑采用“前端草稿 -> 保存项目 -> 后端持久化”的边界。

   `useManagedProject` 或等价 hook 保存一个 dirty draft，用于承载项目名、章节文件列表、输出目录等编辑。点击“保存项目”时一次性提交草稿并刷新项目详情；点击“开始总结”前，如果草稿未保存，复用同一保存流程自动保存。章节文件删除、目录修改、改名等在保存前只改变草稿，不删除后端文件或更新元数据。这样可以避免用户误删章节后，尚未确认就破坏可恢复项目。

8. 导入项目立即设置输出目录并识别状态。

   导入已有项目目录后，后端应把该目录记录为项目级 `custom_output_directory`，并立即扫描该目录中的章节文件、缓存、最终输出和状态文件，计算当前项目状态和可恢复进度。前端导入成功后刷新项目详情和历史列表，不需要等用户点击开始总结才看到状态变化。

9. 输出目录变更需要迁移确认。

   当当前项目的旧输出目录已有文件，且用户把输出目录改为新目录并保存项目时，前端先提示是否迁移已有文件。用户选择迁移时，后端执行受控迁移并更新项目元数据；用户选择不迁移时，只保存新目录，旧文件保留在原位置。迁移失败时保留原项目元数据并返回明确错误，避免出现“目录已改但文件未迁移”的半完成状态。

10. 最少输出字符数作为可配置的 API 有效性校验。

   增加 `minimum_output_characters` 配置，默认值保持兼容（未配置时不改变现有行为，或使用 0 表示关闭）。API 返回后，在写入总结文件和标记任务完成前，对去除标签后的可见正文按字符数计数；低于阈值时视为无效输出，记录失败诊断日志并进入既有重试机制。该校验应适用于小总结、大总结、超级总结和最终总结等所有 LLM 输出阶段。

11. 项目名称输入框保持单行视觉高度。

   项目名称字段应继续使用不能换行的文本输入语义，并通过样式约束高度、行高和垂直 padding，让它看起来就是单行输入框。这个变更只处理观感和误解，不改变项目名规则。

12. 实现提交按同类功能块拆分。

   经审核进入实现后，每完成一个同类功能块并通过对应聚焦检查，应提交一个 git commit。建议提交块包括：项目草稿/保存语义、导入状态识别、输出目录迁移、API 失败日志、最少输出字符数校验、WebUI 细节与验证。提交前不混入未审核的功能或无关格式化。

## Risks / Trade-offs

- 终态刷新可能在后端还未把最新项目状态写入元数据时发生 -> 在终态后拉取 `getTask` 完成，再刷新项目列表；必要时可对当前项目再拉取一次详情。
- 自定义历史项目控件会比原生 select 多一些前端代码 -> 限制变更在 `ProjectHistoryField` 和调用方 hook，避免扩散到每个工作流页面。
- 删除项目是破坏性操作 -> 前端必须确认；后端只删除受管理目录，并对不存在/非法项目返回错误。
- 删除正在运行任务关联的项目会造成恢复信息缺失 -> 删除前端应在确认文案中提示；实现阶段可禁止删除正在运行状态的项目，或允许删除但不影响任务运行。默认采用禁止删除非终态最新任务项目的保守策略。
- 用户级默认导出目录可能被移动或变成文件路径 -> 保存或使用时验证为可用目录；无效时返回提示并回退到当前兜底默认导出目录。
- 用户修改默认导出目录后，旧项目的默认目录展示可能变化 -> 只对没有项目级自定义目录的项目重新计算默认目录；已有项目级自定义目录保持不变。
- 单次失败日志可能包含小说正文、提示词或模型输出 -> 不写入 API key 等敏感值，并在 UI/文档中说明日志可能包含任务内容。
- 前端草稿与后端已保存状态可能短时间不一致 -> 在界面上区分未保存状态；开始总结前统一自动保存并处理保存失败。
- 导入状态识别依赖现有目录结构 -> 识别不到时回退为可开始/未完成状态，并记录可理解提示，不阻止用户手动开始。
- 输出目录迁移可能跨磁盘或遇到同名文件 -> 实现应先规划冲突策略并保证失败不更新元数据。
- 最少输出字符数过高会导致大量重试和成本增加 -> 配置界面应提示其影响，并允许设置为 0 关闭。
