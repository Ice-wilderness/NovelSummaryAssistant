## Context

当前 WebUI 已经通过 `useManagedProject` 加载历史项目，并通过 `useTaskActions` 监听任务事件流。任务完成后，前端会更新任务记录，但不会通知项目历史列表重新读取，因此项目卡片/下拉中的 `latest_task_status` 需要刷新页面后才会变化。

历史项目 UI 目前把“新项目”作为 `<select>` 的空选项，并把状态拼接在项目名之后。长项目名会挤压状态信息；同时选择过一个项目后，再点“新项目”没有明确的重置动作，容易让用户误以为已经切回新项目。后端已有项目列表、加载、改名、清空上传文件和打开目录 API，但没有删除整个项目的 API。

当前默认导出目录固定落在运行时目录下。用户希望配置一个跨项目生效的默认导出目录，同时保留单个总结项目的自定义目录优先级，因此输出目录解析需要明确三层顺序：项目级自定义目录、用户级自定义目录、当前兜底默认导出目录。

## Goals / Non-Goals

**Goals:**
- 任务进入终态后，相关工作流的历史项目列表和当前项目状态自动刷新。
- 历史项目展示改成状态标签前置、项目名独立显示，避免状态被长项目名影响。
- “新项目”成为独立按钮，负责清空当前恢复项目上下文并进入新项目流程。
- 增加删除历史项目入口，删除误建项目时不再需要手动打开资源管理器清理。
- 后端删除仅覆盖受管理的项目工作区和默认导出目录，并从历史列表移除项目。
- 增加用户级默认导出目录配置，并让项目默认输出目录按项目级、自定义用户级、兜底默认值的顺序解析。

**Non-Goals:**
- 不改变任务运行模型、上传文件格式、项目命名规则或恢复算法。
- 不引入实时推送项目列表的新通道；继续复用已有任务事件流和项目列表 API。
- 不删除用户手动指定的自定义输出目录，避免误删 WebUI 管理范围外的内容。
- 不为不同工作流分别增加独立的用户级默认导出目录；本次只提供一个跨工作流的用户级导出根目录。

## Decisions

1. 在任务终态事件处触发项目刷新，而不是轮询项目列表。

   `useTaskActions` 已能识别 `success`、`failed`、`cancelled` 并在终态事件后拉取最新任务。让启动任务的页面在 `startTask` 返回后或终态回调后调用 `project.refreshProjects()`，可以保持反馈及时，同时避免长期轮询。备选方案是定时轮询 `/api/projects`，但会增加空闲请求，也不能解释“为什么此刻刷新”。

2. 给 `useManagedProject` 增加显式 `startNewProject` 和 `deleteProject` 行为。

   `startNewProject` 负责清空 `projectSlug`、项目名、上传文件、输出目录、进度、消息和错误，使按钮语义和状态变化一致。`deleteProject` 调用后端删除 API，随后刷新列表；如果删除的是当前选中项目，则自动回到新项目状态。备选方案是在 `<select>` 的空值上复用恢复逻辑，但这会继续保留“选项即动作”的模糊交互。

3. 将历史项目控件从单一 `<select>` 调整为列表/菜单式控件，并让状态标签成为项目项的首要视觉元素。

   原生 `<option>` 无法可靠承载状态标签、删除按钮和更丰富布局。改成现有表单区中的自定义项目列表/菜单后，可以把状态标签、项目名、更新时间、恢复动作和删除动作分开呈现。若保留 `<select>`，删除按钮和标签样式都难以实现一致体验。

4. 后端删除使用显式 `DELETE /api/projects/{project_slug}`。

   服务层新增 `delete_project(project_slug)`，校验 slug 对应的元数据存在后，删除 `workspace/projects/<slug>` 和 `exports/<slug>`。不删除 `custom_output_directory` 指向的位置，因为它可能是用户选择的任意本地目录。删除不存在的项目返回可操作错误。

5. 用户级默认导出目录作为本地配置持久化，并只影响默认输出根目录。

   增加一个轻量的用户偏好配置，保存 `default_export_directory`。`ProjectWorkspaceService.default_export_dir()` 或等价解析函数读取该偏好后，将项目默认导出目录解析为 `<user_default_export_directory>/<project_slug>/<workflow_subdir>/`；未配置或配置无效时继续使用现有 `<runtime_base>/exports/<project_slug>/<workflow_subdir>/`。项目级 `custom_output_directory` 仍直接覆盖最终任务输出目录。备选方案是把用户级目录写入每个项目元数据，但这会让用户修改默认值后难以影响后续新项目，也会混淆项目级自定义与用户级偏好。

## Risks / Trade-offs

- 终态刷新可能在后端还未把最新项目状态写入元数据时发生 -> 在终态后拉取 `getTask` 完成，再刷新项目列表；必要时可对当前项目再拉取一次详情。
- 自定义历史项目控件会比原生 select 多一些前端代码 -> 限制变更在 `ProjectHistoryField` 和调用方 hook，避免扩散到每个工作流页面。
- 删除项目是破坏性操作 -> 前端必须确认；后端只删除受管理目录，并对不存在/非法项目返回错误。
- 删除正在运行任务关联的项目会造成恢复信息缺失 -> 删除前端应在确认文案中提示；实现阶段可禁止删除正在运行状态的项目，或允许删除但不影响任务运行。默认采用禁止删除非终态最新任务项目的保守策略。
- 用户级默认导出目录可能被移动或变成文件路径 -> 保存或使用时验证为可用目录；无效时返回提示并回退到当前兜底默认导出目录。
- 用户修改默认导出目录后，旧项目的默认目录展示可能变化 -> 只对没有项目级自定义目录的项目重新计算默认目录；已有项目级自定义目录保持不变。
