## Context

当前提示词来源于 `logic/prompts.py` 的 `DEFAULT_PROMPTS`，WebUI 通过 `/api/prompts` 暴露为一组 `{key, filename, text}`，保存后写入 `prompt_cache/*.txt`。运行时通过 `logic.utils.load_all_prompts_for_run()` 读取文本模板，再由 `logic.llm_api.get_llm_summary_with_config()` 执行 `.format()`，最终 `call_llm_api()` 固定发送单条 `{"role": "user"}` 消息。

这次变更跨越前端页面、配置持久化、后端 API、提示词格式化和运行时调用。核心约束是：已有用户的 `prompt_cache/*.txt` 不能丢失，现有工作流的默认行为不能因为结构化配置而退化。

## Goals / Non-Goals

**Goals:**

- 将提示词管理模型升级为“工作流 → 提示词节点 → 消息序列 → 模块引用/文本”的结构。
- 允许每个节点内的消息自定义顺序、角色和内容，并在运行时按顺序渲染为 chat messages。
- 提供提示词模块库，模块可被多个节点消息引用，修改模块后影响引用它的节点。
- 为旧版 `prompt_cache/*.txt` 提供兼容加载和迁移路径。
- 为所有 WebUI 页面补充清晰的说明引导，并保持现有响应式布局。
- 按小功能提交 Git，每个提交都对应一个可运行或可测试的增量。

**Non-Goals:**

- 不新增外部提示词市场、云端同步或多用户权限。
- 不在本次变更中重写小说/文章总结的业务算法。
- 不改变 API 配置、任务运行时和日志系统的基础协议，除非提示词消息格式接入必须扩展。
- 不为章节分割强行引入 LLM 提示词；该页面只补充使用说明。

## Decisions

1. 以结构化 JSON 作为新的提示词主存储，旧文本文件作为兼容输入。

   - 方案：在 `prompt_cache` 下新增一个结构化配置文件，例如 `prompt_workflows.json`，保存 workflows、nodes、messages、modules 和版本号。
   - 理由：多角色、多消息和模块引用不适合继续拆成单个 `.txt` 文件；JSON 可以保留顺序和结构，也便于前后端类型化。
   - 备选：继续为每个节点写多个文本文件。缺点是模块引用、消息顺序和版本迁移会分散到文件命名约定中，校验困难。

2. 使用兼容加载器从现有 `DEFAULT_PROMPTS` 和 `prompt_cache/*.txt` 初始化结构化配置。

   - 方案：当结构化 JSON 不存在时，后端按工作流映射把旧模板转成节点，每个节点默认一条 `user` 消息；`general_prepend_prompt` 转为共享模块或全局前置节点。
   - 理由：用户现有修改能立即出现在新页面，第一次保存后写入结构化 JSON。
   - 备选：启动时立即迁移并删除旧文件。风险较高，不利于回滚。

3. 运行时接受结构化消息，同时保留旧 `text` 字段。

   - 方案：`get_llm_summary_with_config()` 支持将 `messages` 中的内容按同一组变量 `.format()` 渲染；`call_llm_api()` 增加可选 `messages` 参数，没有传入时继续使用单条 `user` 文本。
   - 理由：这是最小改动，可让现有调用路径逐步适配。
   - 备选：一次性把所有调用点改为只传 messages。改动面更大，回归风险更高。

4. 模块引用在后端渲染前展开，前端提供插入和引用入口。

   - 方案：模块有稳定 `id`、名称、说明和内容；节点消息可以保存纯文本内容，也可以保存引用标记。后端渲染时解析模块引用并与消息内容组合。
   - 理由：后端统一展开能保证任务运行和预览一致，也便于测试。
   - 备选：仅在前端插入模块文本快照。实现简单，但模块更新不会同步到引用处，违背“模块化”的预期。

5. 页面说明采用可复用的轻量引导组件，而不是散落在各页面的长段文字。

   - 方案：新增类似 `HelpText`、`FieldHint` 或 `GuidancePanel` 的小组件，页面顶部说明工作流用途，关键字段使用短提示，危险或不可逆操作使用明确文案。
   - 理由：现有 UI 风格偏操作台，短说明和字段 hint 更适合密集表单，不会把页面变成文档页。
   - 备选：单独新增帮助页面。发现性较差，无法直接解释当前控件。

## Risks / Trade-offs

- 结构化配置与旧文本缓存并存可能造成“哪个是最新”的困惑 → 以结构化 JSON 为主；仅当 JSON 不存在时读取旧文件，并在页面显示来源/迁移状态。
- 模块引用如果允许嵌套，可能产生循环引用 → 初版禁止模块嵌套引用，或在后端保存/渲染时检测循环并返回清晰错误。
- 多角色消息会改变部分模型的行为 → 默认迁移保持单条 `user` 消息，用户显式新增 `system` 或 `assistant` 消息后才改变调用结构。
- 工作流节点较多，提示词页面可能过于复杂 → 按工作流分页、节点列表和编辑区拆分，并提供搜索/状态标识；初版优先完成必要编辑能力。
- 页面说明过多可能干扰熟练用户 → 说明采用短文案、可折叠区域或字段 hint，避免大段阻塞主流程。

## Migration Plan

1. 新增结构化模型和加载器，但默认从旧文本模板生成结构化响应，不改变运行时。
2. 前端提示词页改为工作流分页和节点编辑，仍可保存单消息文本，验证与旧行为一致。
3. 增加消息序列和角色编辑，后端保存结构化配置。
4. 扩展运行时格式化和 LLM 调用，使结构化消息真正参与执行。
5. 增加模块库和模块展开逻辑。
6. 补齐所有页面说明引导。
7. 每一步完成后运行对应测试，并提交一次 Git commit。

回滚策略：保留旧 `prompt_cache/*.txt` 读取路径；如果结构化配置出现问题，可临时移除或重命名结构化 JSON，让系统回退到旧文本模板。

## Open Questions

- `general_prepend_prompt` 是作为全局模块、所有节点的前置系统消息，还是保留为可单独编辑的共享节点？建议初版作为“通用前置模块”展示，并允许用户显式引用。
- 自定义总结工作流目前主要使用运行时输入的“自定义指令”。建议初版只为该页面补说明，不把它纳入持久化节点，除非后续要增加默认包装模板。
