# 前端重构前的用户体验优先事项

本文从第二轮稳定性审计中单独抽出会直接影响用户体验、结果可信度或前端重构风险的事项。目标是在后续重构前先处理必要问题；纯内部可维护性、新功能和暂时不影响业务的事项延后。

## 筛选原则

- 用户会直接看到错误状态、误导文案、异常等待时间、费用预期偏差或报告可信度问题。
- 后续前端页面重构会触碰相关状态流、提示文案、任务事件或页面交互。
- 暂不纳入纯内部拆分、未来功能、发布前专项冒烟和低影响工具链 warning。

## 先做

### 1. 雷点扫描旧报告状态兼容提示

- 用户影响：旧版 `failed + findings` 报告当前会被兼容显示为 `completed`，用户可能误以为这是一份完整成功的扫描报告。
- 处理目标：保留旧报告可读性，但在 API 或前端展示中明确这是“历史兼容报告”或“旧版部分失败报告”。
- 建议范围：
  - 后端读取旧报告时暴露 legacy/compat warning 或迁移标记。
  - 前端报告列表和报告详情显示可读状态，例如“历史部分失败”“旧报告兼容显示”。
  - 增加 reporting 与前端展示测试，区分当前 `partial_failed` 和旧报告兼容状态。
- 优先级：高。
- 复杂度：S 到 M。

### 2. LLM/API 重试次数与雷点解析重试语义

- 用户影响：`max_retries` 当前在 LLM API 中表示“总尝试次数”，但雷点扫描解析失败又可能叠加外层重试，导致实际等待时间和 API 调用成本高于用户预期。
- 处理目标：让用户和维护者都能清楚理解一次任务最多会发起多少次请求。
- 建议范围：
  - 将 UI 文案从“重试次数”调整为更明确的“API 总尝试次数”或等价说明。
  - 雷点扫描解析失败重试使用独立概念，例如 `parse_retries`，避免和 API attempts 混用。
  - 增加边界测试，覆盖 API attempts、解析重试和最终失败提示。
- 优先级：高。
- 复杂度：M。

### 3. 任务事件订阅缓存生命周期清理

- 用户影响：`useTaskActions` 的 replay cursor 和 processed event id map 在任务终态后不清理。短期影响很小，但长时间运行大量任务时可能造成前端内存缓慢增长。
- 处理目标：减少长会话风险，并为后续页面重构提供更干净的任务状态边界。
- 建议范围：
  - 在任务进入终态且终态刷新完成后清理该 task 的 cursor 和 seen set。
  - 或设置最大保留任务数，避免历史任务无限积累。
  - 增加 `useTaskActions` focused test。
- 优先级：中。
- 复杂度：S。

### 4. 前端核心页面流回归基线

- 用户影响：这不是当前线上缺陷，但页面重构会触碰任务启动、取消、部分结果、项目状态、雷点报告和分割流程。没有交互基线时，重构更容易引入体验回退。
- 处理目标：在重构前固定关键用户路径，后续可以放心调整页面结构。
- 建议范围：
  - 为小说总结、文章/自定义总结、章节分割、雷点扫描报告查看补最小核心流测试。
  - 至少覆盖任务终态文案、错误/warning 展示、按钮禁用状态和项目状态刷新。
  - 真实浏览器长任务流可先做手工或轻量自动化冒烟，不必一次补完整 E2E。
- 优先级：中。
- 复杂度：M。

## 可顺手处理

### PromptEditor 脏状态判断

- 用户影响：当前使用 `JSON.stringify` 判断提示词是否修改。现有结构简单，风险低；如果前端重构会触碰提示词编辑器，可顺手改成规范化比较函数。
- 优先级：低。
- 复杂度：S。

### raw regex 真实超时

- 用户影响：极端自定义正则仍可能造成慢匹配，但当前已有保守校验和预检，普通用户路径风险已明显下降。
- 建议：除非本轮重构会强化章节分割或开放更复杂 raw regex，否则暂不放进前置任务。
- 优先级：低。
- 复杂度：M。

## 延后

- `workflow_services.py` 整体拆分：这是重要维护项，但不是直接用户体验问题。只有处理雷点报告状态或 retry 语义时顺手拆相关小 helper。
- `project_workspace.py` facade 继续拆分：偏内部结构，先不阻塞前端重构。
- 非小说工作流深度 repair：属于恢复能力扩展，不是当前主要业务路径的前置条件。
- 后续 LLM 聚合方案：这是新功能，应独立设计，暂不和前端重构前置项混在一起。
- Vite/plugin deprecation warning：当前测试和构建通过，等工具链升级时统一处理。
- frozen 打包态本地能力冒烟：发布前需要做，但不应阻塞普通前端页面重构。

## 建议单独 change

建议后续单独开一个小 change，例如 `harden-user-facing-workflow-edges`，只覆盖以下内容：

1. 旧雷点报告兼容状态提示。
2. API attempts 与解析重试语义澄清。
3. `useTaskActions` 终态缓存清理。
4. 前端重构前的核心页面流回归基线。

这组事项完成后，再进入前端页面重构会更稳；其余维护性拆分和新功能可以延后。
