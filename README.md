# NovelSummaryAssistant

基于大语言模型（LLM）的**长篇小说与长文智能总结助手**。能够自动将数千章的网络小说或长篇文章，逐级提炼为结构清晰的多层次总结，涵盖剧情脉络、世界观设定、角色档案与关系网络。

项目提供基于浏览器的本地 WebUI 工作台，支持多 API 并行处理、断点续传、提示词可视化编辑与实时任务日志。

## 核心特性

- **四级递进总结体系**：章节小总结 → 批次大总结 → 超级总结 → 终极总结，层层精炼，信息密度逐步提升
- **剧情与角色分离输出**：剧情总结与角色总结独立生成，使用 `<summary_content>` 和 `<character_content>` 标签结构化包裹，便于程序提取
- **多 API 并行处理**：支持同时配置多个 LLM API（兼容 OpenAI、OpenRouter 及各类代理接口），章节按区段分配给不同 API 并行处理，显著缩短总耗时
- **双重执行模式**：
  - **流水线模式**（默认）：每个 API 独立完成所分配章节的完整总结链
  - **精细分工模式**：所有 API 合力完成小总结和大总结后，统一由自动化调度进行超级总结
- **断点续传**：每个阶段的进度持久化到 `.summarizer_cache/`，任务中断后可随时恢复，不重复已完成的工作
- **可视化提示词编辑器**：所有总结提示词均可在 WebUI 中编辑，支持多消息序列、模块引用、变量插值，修改后实时生效
- **项目持久化**：每个总结任务作为独立项目保存，支持草稿自动保存、文件上传、输出目录管理

## 功能模块

### 1. 小说总结

主要功能。将长篇小说章节文件导入后，自动执行四阶段总结流程。

| 阶段 | 输出 | 说明 |
|------|------|------|
| 小总结 | 单章剧情 + 单章角色 | 每章独立总结，标记信息缺口（留白） |
| 大总结 | 批次剧情 + 批次角色 | 合并相邻章节的总结，串联剧情线，整合角色档案 |
| 超级总结 | 世界观总览 + 剧情总览 + 主要角色 + 关系网络 | 全书级别的高度凝练总结 |
| 终极总结 | 设定集 + 故事通览 + 人物档案 + 关系图谱 | 最终交付成品，语言润色，结构化重组 |

**可配置项**：各阶段目标字数、大总结批次大小、超级总结触发阈值、精细分工模式开关、终极总结指派 API。

### 2. 文章总结

适用于非小说类长文（论文、报告、文档等）。两阶段流程：逐段摘要 → 全文精炼总结（含核心要点提炼）。

### 3. 自定义总结

自由输入提示词指令，选择参考文件，由单个 API 按需生成自定义总结。适合临时性、探索性的总结需求。

### 4. 章节分割

将单个大体积 TXT 文件按章节边界切分为多个小文件，作为小说总结的输入准备。支持三种分割策略：

- **默认策略**：自动识别"第X章/节/回"等中文章节标题
- **正则策略**：用户提供自定义正则表达式
- **标题列表策略**：用户提供完整的章节标题列表

同时支持"卷处理"模式，当章节编号因分卷而重置时自动补偿偏移量。

## 总结工作流详解

### 标签体系

所有 AI 输出遵循统一的结构化标签约定：

| 标签 | 内容 |
|------|------|
| `<summary_content>...</summary_content>` | 剧情与设定总结（核心事件、世界观、伏笔、能力体系） |
| `<character_content>...</character_content>` | 角色信息总结（人物档案、性格演变、关系变化） |

在**小总结**阶段，单次 API 调用同时输出两个标签块；后续阶段（大/超级/终极）中，剧情与角色使用独立提示词分别生成，各自用对应标签包裹。

### 四级流程

```
输入：章节 .txt 文件
  │
  ├─ 1_小总结/剧情/     ← 单章剧情（<summary_content>）
  ├─ 1_小总结/角色/     ← 单章角色（<character_content>）
  │
  ├─ 2_大总结/剧情/     ← 批次剧情整合
  ├─ 2_大总结/角色/     ← 批次角色整合
  │
  ├─ 3_超级总结/
  │   ├─ 剧情_P1/       ← 世界观与核心设定总览
  │   ├─ 剧情_P2/       ← 详细剧情线路
  │   ├─ 角色_P1/       ← 主要角色深度剖析
  │   └─ 角色_P2/       ← 次要角色与关系网络
  │
  └─ 4_终极总结/
      ├─ 剧情_P1/       ← 世界观设定集（精炼版）
      ├─ 剧情_P2/       ← 完整故事通览（叙事版）
      ├─ 角色_P1/       ← 核心人物档案（百科式）
      └─ 角色_P2/       ← 次要角色名录 + 关系图谱
```

### 并行处理架构

```
章节文件: [第1章 ... 第200章]

分布策略（连续区段分配）：
  API-1 → 第1-50章   ──→  小总结 → 大总结 → 超级总结 ──┐
  API-2 → 第51-100章 ──→  小总结 → 大总结 → 超级总结 ──┤
  API-3 → 第101-150章──→  小总结 → 大总结 → 超级总结 ──┤
  API-4 → 第151-200章──→  小总结 → 大总结 → 超级总结 ──┘
                                                          │
                                          指定 API ──→ 终极总结
```

## 快速开始

### 环境要求

- Python 3.10+
- Node.js 18+

### 构建模式（推荐）

```powershell
# 1. 构建前端
cd frontend
npm install
npm run build
cd ..

# 2. 安装 Python 依赖
pip install -r requirements.txt

# 3. 启动
python run_gui.py
```

启动后访问 `http://127.0.0.1:8000`，FastAPI 后端将同时托管前端页面和 API 服务。

### 开发模式

前后端分离运行，支持热更新：

```powershell
# 终端 1：启动后端
python run_gui.py --no-browser

# 终端 2：启动前端开发服务器
cd frontend
npm install
npm run dev
```

开发模式下前端地址为 `http://127.0.0.1:5173`，Vite 自动将 `/api` 请求代理到后端 `http://127.0.0.1:8000`。

### 自定义端口

```powershell
python run_gui.py --host 127.0.0.1 --port 8010
```

## 配置说明

### API 配置（`api_configs.json`）

在 WebUI 的 "API 配置" 页面管理。每条配置包含：

| 字段 | 说明 |
|------|------|
| 显示名称 | API 的唯一标识名称 |
| URL | API 端点地址（兼容 OpenAI 格式） |
| Key | API 密钥（支持明文或环境变量引用） |
| Key 环境变量 | 引用 `.env` 或系统环境变量中的密钥名 |
| Model | 模型名称（可点击"模型"按钮自动获取可用列表） |
| Max Tokens | 最大输出 token 数 |
| Temperature | 生成温度（0-2） |
| Stream | 是否启用流式输出 |
| Timeout | 请求超时（秒） |
| Max Retries | 失败重试次数 |
| 全局启用 | 是否在任务页面中可选择此 API |

### 提示词系统

所有 AI 总结提示词均可在 WebUI 的 "提示词" 页面进行可视化编辑：

- **工作流**：小说总结（11 个节点）、文章总结（2 个节点）
- **消息序列**：每个节点支持多条消息，可指定角色（system/user/assistant）
- **模块引用**：支持 `{{module:模块名}}` 语法插入可复用的提示词模块
- **变量插值**：提示词中的 `{变量名}` 会在运行时自动替换（如 `{plot_word_count}`）
- **脏标记**：被修改过的节点会显示"已修改"标记，支持一键重置为默认值

用户修改后的提示词保存在 `prompt_cache/prompt_workflows.json` 中（不纳入版本控制）。未修改时，自动使用 `logic/prompts.py` 中的内置默认值。

### 用户设置（`user_settings.json`）

- **默认输出目录**：总结结果文件的默认保存位置
- **最低输出字数**：API 返回内容低于此字数时自动触发重试（0 = 不限制）

### 项目工作区（`workspace/`）

每个总结任务作为独立项目持久化：

- 项目元数据（名称、类型、自定义输出目录）保存在 `project.json`
- 上传的源文件存储在项目子目录中
- 支持草稿自动保存、文件上传、项目导入导出

## API Key 策略

API Key 支持三级来源，优先级从高到低：

1. **系统环境变量**
2. **项目根目录 `.env` 文件**
3. **`api_configs.json` 中的明文 key**

配置示例 — 在项目根目录创建 `.env`：

```text
MY_OPENAI_KEY=sk-xxxx
```

然后在 WebUI 的 API 配置页中，将对应 API 的"Key 环境变量"字段填写为 `MY_OPENAI_KEY`。

WebUI 在展示和保存时会自动遮蔽 key 值（显示为 `****` + 末四位），保存遮蔽值时不会覆盖已有的真实 key。

## 已知限制

- 浏览器沙箱限制，WebUI 无法直接读取任意本地绝对路径；文件操作以手动输入、粘贴或 Web 上传为主
- 总结质量高度依赖所配置的 LLM API 能力与可用性
- 旧版 CustomTkinter 桌面 GUI 已移除，统一采用 WebUI 作为本地交互入口
- 生成内容的准确性取决于 AI 本身，对关键信息的核验建议人工复核
